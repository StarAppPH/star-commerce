# DO NOT DO — Architecture Rules for starCommerce

These rules are enforced by code reviewers. Violating them will get your code rejected.

---

## Logic

- Do NOT swallow errors silently. Every `except` must log or re-raise meaningfully.
- Do NOT leave dead code or unreachable branches.
- Do NOT use magic numbers or strings. Define constants at the top of the file.
- Do NOT assume execution order without guarantees.
- Do NOT skip cleanup on premature returns — use `try/finally`.
- Do NOT copy-paste logic. If it appears twice, extract it.
- Do NOT leave incomplete switch/map/enum handling — cover all cases.
- Do NOT mutate data unintentionally. Be explicit about state changes.

---

## MongoDB

- Do NOT filter, sort, or aggregate data in Python when MongoDB can do it.
- Do NOT fetch entire collections — always use projections to return only needed fields.
- Do NOT use transactions for single-document operations — only for multi-document atomic writes.
- Do NOT create queries that skip indexes or cause full collection scans.
- Do NOT use `$lookup` and `$unwind` unless absolutely necessary.
- Do NOT put `$match` late in an aggregation pipeline — filter early.
- Do NOT load large result sets into memory — use pagination.
- Do NOT design data models without considering 10x data growth.

---

## Security

- Do NOT pass raw user input into MongoDB queries — always validate through Pydantic models first.
- Do NOT return sensitive fields (passwords, tokens, secrets) in API responses.
- Do NOT hardcode secrets — use environment variables.
- Do NOT expose internal details in error messages (stack traces, DB structure, file paths).
- Do NOT trust client-side data without server-side validation.
- Do NOT use string concatenation to build queries.
- Do NOT set CORS to allow all origins in production.
- Do NOT skip authentication or authorization checks on any protected endpoint.
- Do NOT store secrets in code or config files committed to git.

---

## Testing

- Do NOT run tests outside `ENVIRONMENT=localdev`, or against any DB but a `*Scratch` one (`databaseName=teststarCommerceScratch`) — conftest refuses both, and tests wipe the DB. The default `teststarCommerce` DB holds the restored prod dump.
- Do NOT run `pubSubMockDataGenerator.py` against the default DB either — it wipes the selected DB and does not check its name.
- Do NOT write `pubSubMockDb` from tests — publishes are recorded in memory (`lastPublishedPayload`).
- Do NOT pin a route's shape with validation alone — use `assertExactShape` (validation plus exact keys).
- Do NOT return a deliberately unmodelled shape from a route test without the `responseCheckOff` fixture.
- Do NOT use pytest fixtures or test classes — use top-level `test_` functions with inline setup (the conftest helpers and its "Sign-in" fixtures are the exceptions).
- Do NOT forget `wipeDatabase()` in `finally` for any test that writes to the DB.
- Do NOT forget to call `wipeDatabase()` as the FIRST line inside `try:` for idempotency.
- Do NOT use snake_case for local variables in tests — use camelCase.
- Do NOT hardcode test data as raw dicts — build it with the models and the conftest helpers (`createTestUser`), or with factory helpers in an `objectGeneratorForTesting.py` once you add one.
- Do NOT call APIs via HTTP test client — call `ApiRequests()` methods directly. Only `test_route_responses_http.py` may, because it tests the generated transport layer itself.
- Do NOT only assert return values — verify DB state independently with `db.read(...)`.
- Do NOT write separate test functions for error cases — use `pytest.raises` inline within the workflow.
- Do NOT write granular unit-style tests for integration logic — chain operations in long integration flows.
- Do NOT forget `publishToProdPubSub=False` in tests where the parameter exists.
- Do NOT modify assert statements in existing tests to make them pass — fix the production code instead.

---

## Architecture

- Do NOT edit `app.py` or `appPubSub.py` — they are auto-generated by `AppCreator.py`.
- Do NOT edit `ServerRequests.ts`, `Server.ts`, `ApiResponse.ts`, `serverConstants.ts` or `schemas/*.ts` — they are auto-generated.
- Do NOT put database calls in Pydantic model classes (the `objects/` package) — all DB operations belong in action files or `ApiRequests.py`.
- Do NOT use plain `BaseModel` for models with `str | None` fields — use `MongoModel` (DB documents) or `AppModel` (embedded/non-persisted) to get automatic empty-string-to-None coercion.
- Do NOT return raw variables from `@route_config` or `@pubSubDecorator` functions — always return a dict with explicit keys.
- Do NOT create API methods without type annotations on every parameter — AppCreator uses them for TypeScript generation.

---

## Routes and response models

Why each rule exists is in `ARCHITECTURE.md`, section "Typed API Responses".

- Do NOT add an `ApiRequests` route without `@route_config(responseModel=<objects model>)` — AppCreator refuses to generate. Only `PubSubRequests` push handlers are exempt.
- Do NOT return a raw list or primitive — wrap it in a dict with an explicit key. A dict is returned as is.
- Do NOT use a `RootModel` response, or add a route to `CROSS_REPO_BARE_RESPONSE_ROUTES`, unless another service already reads that route's `data` as the bare value. Never reshape a route another repo calls.
- Do NOT reshape a `@pubSubDecorator` route's return value — it IS the payload the consumers receive. Keep `@pubSubDecorator` the outer decorator and pin the payload with `lastPublishedPayload` in a test.
- Do NOT write a projection by hand for a response — derive it with `projection_of(Model)`.
- Do NOT use a database model (`MongoModel`, `AppModel`, a `*View`) as a responseModel or a publisher's payload model, nor nest one inside a `ResponseModel`, nor make a `ResponseModel` inherit one.
- Do NOT send whole stored documents in a list route when the caller reads part of them — add a row model (`WHOLE_DOCUMENT_ROWS` lists the exceptions).
- Do NOT restate a domain field in a row model without a `MIRRORS` entry.
- Do NOT annotate a route param as `datetime`, `date` or `time` — use `str` and parse it with `utils.appDayStart` / `appDayBounds` (ISO `YYYY-MM-DD`) or `utils.parseIsoInstant` (ISO 8601 date-time).
- Do NOT leave a route param unannotated, give it a `None` default without `| None`, or type it as a bare `dict` / `list` / `tuple` / `Any`.
- Do NOT write a validator whose error message includes the value, or one that mutates its input (`mode='before'` validators are copy-on-write).
- Do NOT type a response field as `dict[str, X]` keyed by customer data, or type a `SECRET_RESPONSE_KEYS` key (AppCreator refuses; declare it `SkipJsonSchema`).
- Do NOT trust a client-supplied identity on login — `loginWithGoogle` verifies the Firebase `idToken`; the raw uid/email (and `devLogin`) is accepted in localdev only.
- Do NOT log request values — the generated routes log which of their params a POST sent, and a `createAccessToken` route nothing at all.
- Do NOT add `roleAccess` to a route without `jwtRequired=True` — route_config refuses it: the role check trusts the userId the body sends, which only a JWT route ties to the caller.
- Do NOT put a `@computed_field` on a model a route returns — the generated TS type declares it as present, but the route returns a raw dict that never carries it.
- Do NOT bind a local run to every interface by default — `LOCAL_BIND_HOST=0.0.0.0` in `server/.env` is an explicit, announced opt-in: localdev accepts a raw sign-in identity.
- Do NOT deploy with a `JWT_SECRET_KEY` under 32 random characters or the placeholder — app.py refuses it outside localdev.
- Do NOT use GET/HEAD methods with parameters — they are blocked by `route_config`.
- Do NOT set both `createAccessToken=True` and `jwtRequired=True` on the same endpoint.
- Do NOT run the Flask server from inside the `server/` directory — run from the project root with `python server/app.py`.
- Do NOT bypass the service dev-port check by editing the generated `app.py` port or hand-editing a `services/<name>.py` `dev=` URL to whatever makes `AppCreator.py` pass — the port lives in `AppCreator.py` `PORT` (this repo) and in the sibling repo's `AppCreator.py` `PORT` (its `dev=` URL); change it there and regenerate.

---

## File Upload

- Do NOT accept HEIC or HEIF files — block both file extension (`.heic`, `.heif`) and MIME type (`image/heic`, `image/heif`).
- Do NOT use `accept="image/*"` for photo inputs — use `accept="image/jpeg,image/png,image/webp"` explicitly.

## Pub/Sub

Why each rule exists is in `ARCHITECTURE.md`, sections "Pub/Sub Integration" and "Pub/Sub mock messages & contract tests".

- Do NOT publish to both production Pub/Sub and mock DB at the same time — `pubSubDecorator` raises.
- Do NOT skip idempotency checks — every message must be deduplicated by `messageId`.
- Do NOT use service account credentials in production environments — use default credentials.
- Do NOT pass `publishToPubSubMockDb=True` anywhere except `pubSubMockDataGenerator.py` — it is the only writer of this repo's `pubSubMockDb` collection, and a stray call from a test corrupts every consumer's replay.
- Do NOT give `publishToProdPubSub` a default value on a `@pubSubDecorator` method (the decorator raises at import), and do NOT call one without passing `publishToProdPubSub` explicitly (`test_ifAllPubSubFunctionsGenerated` fails on any call site in the top-level `server/*.py` files).
- Do NOT let a `PubSubRequests` handler raise on a benign missing document (already deleted, never synced) — a raise → 400 → GCP retries up to `max_delivery_attempts` (5) and then dead-letters the message. Return the idempotent shape (`{'updated': 0}`, `{'deleted': False}`, the existing doc) and raise only on a genuine data fault.
- Do NOT write a handler that inserts twice when the same payload is redelivered — look the document up by its natural key first. The route's messageId de-dupe catches most redeliveries, but a crash between the handler and the 200 redelivers the same messageId; `REDELIVERY_STEPS` replays every message twice to prove the handler copes.
- Do NOT add a handler without a `REPLAY_STEPS` + `REDELIVERY_STEPS` entry in `test_pubSubContracts.py`, and do NOT park it in `UNTESTED_PUBSUB_FUNCTIONS` to get green — that list is only for handlers no publisher will ever address (`ping`, `createDeadLetter`).
- Do NOT edit the "Shared AST helpers" or "Static contract tests" region of `test_pubSubContracts.py`, or any other file create-star-app's `fleet/sharedFiles.json` lists (`servicePortCheck.py`, `test_file_sizes.py`, the `pubSubMap*.py` tools, ...), in one repo — `test_sharedFiles.py` fails. Fix the template in create-star-app, commit it, then run `cd server && python sharedFileCheck.py --write` in every repo.
- Do NOT edit `pubsub_map.json` or `PUBSUB_MAP.md` by hand — run `cd server && python pubSubMap.py --write` (AppCreator runs it too) and commit both. A contract change is done only when every repo of the fleet has regenerated and committed its map, with the same branch name checked out in every repo or after merging to `main` (siblings are read at this repo's branch name if they have it, else at `main`). `--write-all` regenerates every sibling checkout on this branch at once; the commits stay manual.
- Do NOT hide a publisher from `pubSubAdmin.py` — its topic would never be created (`test_publishersAreWherePubSubAdminLooks`). Write it as a plain `def` (not `async def`) in `server/*.py` or `server/actions/*.py`, decorated exactly `@pubSubDecorator(projectNameConsumers=[...])`: never `@pubSub.pubSubDecorator`, never positional consumers, never a variable list, and only known consumers whose names match a `services/` class name (case-insensitive). Do NOT call `publishMessage` by hand on a topic that is not built from a `@pubSubDecorator` function's `__name__` (`test_handPublishSitesUseADecoratedTopic`).
- Do NOT try to silence a payload/handler mismatch: fix it at its source (the publisher's payload model or the consumer's handling; `python pubSubMap.py --explain <handler>` shows both sides). `PUBSUB_CONTRACT_GAPS` is retired: do NOT define it, even empty (`test_escapeHatchesAreLive` fails on it). `PUBSUB_MESSAGE_MODELS` is retired too: a handler parses its message with its generated `<Fn>Message`, once, and reads `data` only in an `except ValidationError:` fallback on that parse.
- Do NOT accept an idempotent no-op shape (`{'updated': 0}`, `{'deleted': False}`, an already-stored doc) as the outcome of a FIRST delivery in `REPLAY_STEPS` — that means the seed created what the handler should have, or the handler silently skipped. Those shapes are asserted in `REDELIVERY_STEPS` only.
- Do NOT seed the document a handler itself creates — seed only the prerequisites it reads that no earlier message creates.
- Do NOT key `REPLAY_STEPS` / `REDELIVERY_STEPS` with a string or with `pubSubRequests.<handler>.__name__` — only `PubSubRequests().<handler>.__name__` is visible to `test_ifAllApiRequestTested`'s AST scan.
- Do NOT define a second `REPLAY_STEPS` / `REDELIVERY_STEPS` below the empty one — extend the existing definition, a rebind silently discards entries.
- Do NOT run two repos' test suites or `pubSubMockDataGenerator.py` at the same time — they all share the one local `pubSubMockDb`.
- Do NOT run a consumer's suite before every publisher's generator has run (rows expire after 3 days), and do NOT edit or back-date a `MockData` row — re-run the publisher's generator.
- Do NOT delete or truncate another repo's `pubSubMockDb` collection — a generator rebuilds only its own.
- Do NOT reorder `test_atExitValidation` — it must stay last and run in the same process as the replay.
- Do NOT leave a consumer in `SERVICES_WITHOUT_MOCK_DATA_YET` once its repo has mock data — the drift guard for that consumer is silently off.
- Do NOT expect a consumer's `pubSubAdmin.py` to create its subscriptions — the PUBLISHER's `pubSubAdmin.py` creates `<function>_<publisher>_to_<consumerService>`, and must run before the publisher deploys (`checkPubSubTopics`, in the predeploy job, fails the deploy on a missing topic).

## TypeScript / Frontend

- Do NOT use `any` type — always use proper types from the generated `@/app/schemas/` (this project has no `app/types/index.ts`).
- Do NOT cast a server response (`res.data as X`, `as unknown as X`) — narrow `ApiResponse<Model>` (from `@/app/api/ApiResponse`) with `res.status === 200`.
- Do NOT import `schemas/ApiResponseSchema` outside `app/api/` — `npm run lint` refuses it (`next build` does not run that rule).
- Do NOT send the Firebase uid or email to `loginWithGoogle` — send `{ idToken }` only (`AuthContext.signInWithGoogle`).
- Do NOT `.slice()` or `split('T')` a server datetime — Flask sends RFC 1123 (`Sun, 04 Oct 2026 08:00:00 GMT`). Parse it with `new Date()` and send dates to routes as ISO strings.
- Do NOT consider frontend work complete until `npm run build` passes.

---

## Modals

- Do NOT use HTML5 `<dialog>` element or `showModal()` for modals — it creates a browser top-layer that breaks `document.elementFromPoint()` and dev tooling (alt+hover component inspection).
- Do NOT use any modal library that renders via `<dialog>` internally.
- DO use a `<div>`-based modal with `createPortal(...)` to `document.body`, with:
  - `position: fixed; inset: 0; z-index: 50` for the overlay container
  - A separate backdrop `<div>` with `bg-black/50`
  - Escape key handling via `document.addEventListener('keydown', ...)`
  - Scroll lock via `document.body.style.overflow = 'hidden'`
  - Backdrop click via `e.target === e.currentTarget`
- See `Modal.tsx` in the components directory for the reference implementation.
