# CLAUDE.md

## Global Preferences

### Flask JWT Convention
- In a Flask app, ensure JWT is implemented.
- JWT checks are auto-generated by `AppCreator.py`.
- The check code is `if userId == current_user` and only applies to generated functions that have a `userId` parameter and a `@jwt_required` decorator.

### Route Return Convention
- All functions decorated with `@route_config` or `@pubSubDecorator` must return a dictionary with explicit keys.
- Never return a raw variable (string, list, number).
- If the return value is already a dict (e.g., a document from `model_dump()`), return it directly — do NOT wrap it in `{'data': ...}`.
- Only use `{'key': value}` wrapping when the value is a list or primitive.
- This is critical for `@pubSubDecorator` functions because the return value IS the PubSub message payload that consumer services receive.
- Examples:
  - WRONG: `return sampleData` (raw variable, not a dict)
  - WRONG: `return {'data': salesOrder.model_dump(by_alias=True)}` (unnecessary wrapping of a dict)
  - CORRECT: `return salesOrder.model_dump(by_alias=True)` (already a dict with explicit keys)
  - CORRECT: `return {'categories': categoryNames}` (wrapping a list with an explicit key)

### File Upload Convention
- Block HEIC and HEIF file uploads in all file uploading functions.
- Check both file extension (`.heic`, `.heif`) and MIME type (`image/heic`, `image/heif`).
- Throw an error with a message instructing the user to convert to JPG or PNG before uploading.
- All photo/image file inputs must use `accept="image/jpeg,image/png"` instead of `accept="image/*"`.

### Flask Server Startup
- Always start the Flask server from the **project root** using `python server/app.py`.
- Do NOT `cd` into the `server/` directory first — the app uses relative paths (e.g., `server/keys/`) that assume the working directory is the project root.

### gcloud Read-Only Rule
- This applies to Claude and to every spawned agent.
- Use `gcloud` (and `gsutil` / `bq`) for READ-ONLY operations only: `list`, `describe` (except Cloud Run, see below), `get-iam-policy`, `logging read`, etc.
- Never create, update, deploy or delete any GCP resource. That includes Cloud Run services, jobs and revisions (`deploy`, `update`, `execute`, `delete`), Pub/Sub topics and subscriptions, Cloud Scheduler jobs, IAM bindings, secrets, buckets and gcloud config (`gcloud config set`).
- Never run a script that writes to GCP either (e.g. `pubSubAdmin.py` without `--dry-run`, `update_all_jobs.bat`, `create_or_update_job.bat`, `run_job_once.bat`).
- When a change is needed, give the user the exact command or script to run themselves (they can run it in-session with `! <command>`, or in their own terminal if a deny rule blocks it), then verify the result with read-only commands.
- Never read secret or credential values, even with read-only commands. Cloud Run `describe` and `--format=json|yaml` print env vars (DB URIs, JWT keys) in plain text; use `list` and `--format="value(...)"` without env fields. Never run `gcloud secrets versions access` or `gcloud auth print-*-token`.
- Never pull a credential from cloud config to connect to a production database or API, even to read. A credential that can read prod can usually write it.
- For production data use the local dump: `server/tools/dumpProdDataToLocalDev.cmd` restores into the local `test<projectName>` DB. pytest wipes that DB, so warn before running tests when the dump matters.
- `permissions.deny` in `~/.claude/settings.json` enforces part of this. Never work around a denied command (e.g. with a script that shells out to gcloud).

### Sound Notification
- All agents and Claude (non-agent mode) should play a notification sound when presenting output to the user.
- Use: `powershell -c "[System.Media.SystemSounds]::Hand.Play(); Start-Sleep -Milliseconds 1000; [System.Media.SystemSounds]::Beep.Play(); Start-Sleep -Milliseconds 1000; [System.Media.SystemSounds]::Hand.Play(); Start-Sleep -Milliseconds 1000; [System.Media.SystemSounds]::Beep.Play()"`

### Code Change Approval
- This rule applies ONLY to the orchestrator/main Claude, NOT to spawned agents.
- When you (the orchestrator) are about to write code directly, present the proposed changes and wait for explicit user approval.
- Spawned developer agents are allowed to write code autonomously after the user has approved their plan — do not make them wait for per-file approval.

### Test Assert Rule
- Never modify assert statements in existing tests to make them pass. Asserts are the source of truth.
- If a test fails, fix the production code or fix the test setup/data — never change the expected values in asserts.


### TypeScript Strict Typing Rule
- Never use `any` type in TypeScript code. Always use proper types.
- Use generated schema types from `schemas/` directory (e.g., `ReceivingEntryUnit` from `ReceivingEntryUnitSchema.ts`).
- For types not available as generated schemas (e.g., User, Customer, Supplier), use the types defined in `app/types/index.ts`.
- API responses should be typed with `ApiResponse<T>` from `app/types/index.ts`.
- This rule applies to all frontend TypeScript code in both the React and Next.js clients.

### Data-Component Attribute Convention
- All core interactive elements in frontend components must have a `data-component` attribute.
- This includes: inputs, selects, checkboxes, radio groups, buttons, form sections, and reusable components (AsyncAutocomplete, ImageUploader, FormField, etc.).
- Naming convention: camelCase `{formName}{FieldName}` (e.g., `createUnitName`, `createUnitSubmit`, `createUnitIsForSale`).
- Reusable shared components should accept a `dataComponent` prop and apply it as `data-component` on their root element, falling back to a generic default if not provided.

### Console.log Cleanup Rule
- Flag and remove any `console.log` in client code that exposes sensitive data (user objects, auth errors, API responses, tokens, environment variables, signed URLs).
- All `console.log` statements should be removed from production code except for intentional error logging in catch blocks (use `console.error` for those).
- Acceptable exceptions: Cypress test files, dev-only tools (e.g., DevClickToComponent).

### Next.js Image Optimization Rule
- Never use `<img>`, `CardMedia` with image URLs, or `background-image` for user/product/content images in Next.js projects.
- Always use `next/image` (`import Image from 'next/image'`) for all image rendering to leverage Vercel's automatic optimization (WebP/AVIF, resizing, CDN caching).
- MUI `Avatar` with text initials (no image src) is acceptable.

### Snackbar for POST Response Feedback
- When a UI button triggers a POST request via `serverRequests`, always use `useSnackbar()` from `SnackbarContext` and call `showApiResponseSnackbar(res)` with the response.
- Never use ad-hoc error state (`useState<string | null>` + inline error display) for server response feedback.
- All server responses from POST actions must go through the app's unified Snackbar.

### No DB Queries in Model Classes
- Pydantic model classes (e.g., in the `server/objects/` package) must never import or call database functions (`db`) directly.
- All database reads and writes belong in action functions (e.g., `server/actions/`).
- Models should only contain pure business logic, validation, and data transformation.

### Empty String Coercion Convention
- Any `str | None` field that receives `""` from the client must be treated as `None` on the backend.
- Ensure the server never stores or processes `""` for optional string fields — it must be `None`.

### Merge to Main: Leave the Primary Checkout on main
- This applies to Claude and to every spawned agent.
- The primary checkout is the repo folder the user works in (e.g. `C:\Users\Adrian\Documents\GitHub\<repo>`), not a `_wt\...` worktree.
- Prefer merging in the primary checkout: switch it to `main`, merge, run the full suite, then push from there.
- If the merge happens in a worktree (because the primary checkout has unrelated work in progress), finish after the push in every repo the merge touched:
  - `git -C <worktree> switch --detach` (git lets only one folder hold `main`)
  - `git -C <primary checkout> switch main`, then `git -C <primary checkout> pull --ff-only`
- Keep uncommitted changes. Never stash, reset or discard them to make the switch work. If git refuses, stop and tell the user.
- End every merge report with each repo's branch, HEAD and `origin/main`, so a checkout left behind is visible.
- Why: tools like `run_job_once.bat` read the primary checkout's files. A checkout left on an older branch hides new job files, so the user runs the wrong job.

## Agent System

### How to read agent files

- Agents in .claude/agents/ may reference a template using `template: <name>`
- When you see a template reference, read the corresponding file from .claude/templates/
- Substitute all {PARAMETERS} listed in the agent file into the template
- Agent groups in .claude/groups/ define lists of agents. When a template references a group, read the group file to get the list.
- Agent context files can be found in .claude/context/

### Available Agents
- All agent definitions are stored in `.claude/agents/`. Read each `.md` file in that directory to discover available agents and their roles.

### Rules

- Never write code yourself unless user tells you
- If a task is unclear, ask user for clarification before assigning
- Track which agents have been assigned and their current status
- Auto-accept reviewer and debater results when they reach agreement. Only escalate to the user when there is an unresolved disagreement or after 2 revision cycles without approval.
- Do not present work to user until all reviews are resolved (auto-accepted or escalated decisions are made)
- Launch backend-tester and ui-documenter in parallel when both are needed for a task. Skip backend-tester for frontend-only tasks. Skip ui-documenter if no user-facing logic was added or changed.
- Skip datetime-reviewer for frontend-only tasks. Datetime review is only needed for backend code (storage, serialization, timezone handling). Frontend datetime concerns (use `toISOString()`, don't send locale strings) are simple enough for the logic-reviewer to catch.
- Launch dry-reviewer for both backend and frontend tasks. Frontend duplication (repeated fetch patterns, inline formatters, copy-pasted components) is just as harmful as backend duplication.
- Launch data-efficiency-reviewer for tasks where frontend code calls backend endpoints (via `serverRequests`), even if the backend code itself wasn't modified. Also launch for tasks that modify a backend endpoint consumed by existing frontend code. Skip only for pure frontend-only tasks with no API calls (e.g., styling, layout) or pure backend-only tasks with no frontend consumer in the changeset.
- Skip seo-reviewer and nextjs-reviewer for backend-only tasks (no `.ts`/`.tsx` files changed). Launch both for any task that touches frontend pages or components. SEO review checks server-rendered content, meta tags, crawlability, and structured data. Next.js review checks proper Server Component / Client Component boundaries, 'use client' correctness, and data fetching patterns.

### Agent Spawning & Communication

- **Always spawn developer agents with `mode: "auto"`** so they don't silently block on permission prompts.
- **Agents must NEVER use `AskUserQuestion` directly.** All questions must go through `SendMessage` back to the orchestrator, who relays to the user.
- **Every agent must `SendMessage` back to the orchestrator when done**, whether it succeeded, failed, or needs clarification. Silent completion is never acceptable.
- If an agent needs user input, it must `SendMessage` its question to the orchestrator and stop. The orchestrator asks the user, then `SendMessage`s the answer back to the agent.
- When spawning agents, always set a `name` so you can address them via `SendMessage` later.

Git Bash syntax: `VAR=value command`. In PowerShell set the variables first (`$env:ENVIRONMENT = 'localdev'`).

```bash
python -m venv server/venv              # Create the venv (once)
source server/venv/Scripts/activate     # Activate venv (Windows Git Bash)
pip install -r server/requirements.txt  # Install deps
ENVIRONMENT=localdev python server/app.py   # Run server on 127.0.0.1:5003 (from project root; LOCAL_BIND_HOST in server/.env opens it to the LAN)
cd server && ENVIRONMENT=localdev python AppCreator.py   # Regenerate routes + TS client (needs json2ts: npm i -g json-schema-to-typescript@15)
cd server && ENVIRONMENT=localdev databaseName=teststarCommerceScratch pytest -n auto   # Run the full suite (it wipes the DB: a *Scratch DB only; parallel workers, as many as free RAM holds; needs pytest-xdist, once per venv: pip install -r server/requirements.txt, never commit venv files)
cd server && ENVIRONMENT=localdev databaseName=teststarCommerceScratch pytest test_<file>.py[::test]   # One file or a few tests: one process (workers would each load the app first, slower for small runs)
cd server && ENVIRONMENT=localdev databaseName=teststarCommerceScratch python pubSubMockDataGenerator.py   # Pub/Sub mock data (wipes the selected DB, and does not check its name)
cd server && python pubSubMap.py --write      # Regenerate the Pub/Sub map (AppCreator runs it too); no flag: exit 0 only when fresh and clean for this repo, as test_pubSubMap.py; --explain <topic>
cd server && python pubSubModels.py --pull    # Regenerate server/objects_<publisher>.py from each publisher's pubsub_models.json (AppCreator runs it too); no flag: check; --push: pull in every same-branch consumer; ENVIRONMENT=localdev ... --write-manifest: this repo's pubsub_models.json
cd server && python sharedFileCheck.py --write   # Take create-star-app's version of the shared files; no flag: check
```

- **AI agents** running tests: run a suite in the FOREGROUND (Bash `timeout` up to 600000), and never end the turn waiting on a background run (background-completion notices do not reach spawned agents). On a RAM-gate refusal (exit code 75, `Not enough RAM to run tests`) wait for the other run to finish; never override it.

## Architecture

- **Code generation**: AppCreator.py generates `app.py`, `appPubSub.py`, `ServerRequests.ts`, `Server.ts`, `ApiResponse.ts` and `schemas/*.ts` from `ApiRequests.py`, `PubSubRequests.py` and the `objects/` package (one module per domain, re-exported by `objects/__init__.py`), plus `server/mcpServer.py` (mcpCreator.py) and `server/chatTools.py` (chatToolsCreator.py, the chat route's tools, from the same `@mcp_tool` specs), plus `client/lib/generated/serverConstants.ts` from `sharedConstants.py` (regenerate that one alone with `python AppCreator.py --constants-only`), and last refreshes `server/pubsub_map.json` + `server/PUBSUB_MAP.md`. Do not edit generated files.
- **Service-to-service routes**: routes another service calls over HTTP go in `server/actions/ServiceToServiceActions.py` (a mixin of `ApiRequests`). Their response is a contract with that service: the unused-response-field gate skips them, and fails on a route a sibling calls that is not there, or one there that no sibling calls. Each one declares `@route_config(serviceOnly=True)` (and no other route does): outside localdev it answers only a caller with a Google ID token from `callerAuth.SERVICE_CALLER_ACCOUNTS`, which `services/__request.py` sends on Cloud Run.
- **Caller auth** (`callerAuth.py`, shared): every Pub/Sub push handler checks the push's OIDC token (`PUSH_SERVICE_ACCOUNTS`, audience = the push URL) and every `serviceOnly` route its caller's ID token; a refusal is a 401. Skipped in localdev only. `CALLER_AUTH_MODE=report` with an unexpired `CALLER_AUTH_REPORT_UNTIL` on a service logs refusals and lets them through (the rollout phase, which ends by itself on that date); unset, past that date, more than 30 days ahead or without a readable one, it enforces. The accounts live in callerAuth.py's per-repo block; pubSubAdmin.py gives every push subscription `PUSH_SERVICE_ACCOUNTS[0]`.
- **Database**: MongoDB, PyMongo singleton via `mongoDb.py`, optimistic locking with `_version`.
- **Connection budget**: the services share one Atlas Flex cluster that caps connections. One connected client is about 6 monitor sockets on a 3-member set plus pool sockets on demand (one per operation in flight), times every process (instances, gunicorn workers, job tasks); an idle instance keeps them until scale-down, so `--min-instances` above 0 holds its share for good. So a cloud process holds one real client (`db`), the Dockerfile's single gunicorn worker stays single (its `--threads 8` share that one thread-safe client: they add pool sockets on demand, never monitor sockets), and any other `MongoClient` built at import uses `connect=False`. `pubSubMockDb` is built that way and never written in the cloud. Do not add `maxPoolSize`; cap max instances instead (cloud-setup sets 10). `test_mongoDb_cloud_clients.py` pins it, and a missing or empty `MONGO_URI` fails fast.
- **Production data locally**: `server/tools/dumpProdDataToLocalDev.cmd` restores prod into `teststarCommerce`. Its source, first found wins: `MONGO_DUMP_URI` in the environment, `MONGO_DUMP_URI` in `server/cloud.env` (written by cloud-setup), or `MONGO_DUMP_HOST` + `MONGO_DUMP_USER`, with mongodump asking for the password (masked). With a URI the password is on mongodump's command line: use a read-only user. The tests wipe their `*Scratch` DB, never that one.
- **Auth**: Firebase + JWT (Flask-JWT-Extended).
- **Typed API responses** (details in `server/ARCHITECTURE.md`):
  - Every `ApiRequests` `@route_config` route declares `responseModel=<objects ResponseModel>`; AppCreator refuses to generate without one. `PubSubRequests` push handlers are exempt.
  - A responseModel, and every Pub/Sub publisher's payload model, is a `ResponseModel` all the way down: every nested model too, inheriting from `ResponseModel`s only, never a database model (`MongoModel`, `AppModel`, `StoredDocumentKeys`, `*View`). AppCreator refuses otherwise, naming the model's file:line (`responseModelCheck.py`); a test asserts it.
  - A `RootModel` (bare list or number) is refused except for the routes in `AppCreator.CROSS_REPO_BARE_RESPONSE_ROUTES` (each with its reason and consumers; a test pins the map; empty in a new project). Never add a route to avoid wrapping its answer.
  - AppCreator generates `Promise<ApiResponse<Model>>` methods plus the `RouteResponseModels` / `RouteRequestBodies` / `PublicRoute` maps.
  - `ApiResponse<T>` comes from `@/app/api/ApiResponse` (`client/app/api/ApiResponse.ts`): `ApiSuccess<T>` (200) | `ApiFailure` (0/400/401/403, `data: null`). The client uses `fetch`; a JWT rejection's `{msg}` body becomes a 401 envelope (and fires `jwt-expired`), a network error or non-JSON body a status-0 envelope. Narrow with `res.status === 200`; never `res.data as X`. (This overrides the global rule's `app/types/index.ts`, which this project does not have.)
  - A `ResponseModel` declares exactly what the route sends: the localdev check rejects an undeclared key at any depth. Read with `projection=projection_of(Model)` (never a hand-written projection), or build the dict; drop what the route read for itself (`projectedCopy(Model, doc)`). Stored documents are typed with `*View` models (`StoredDocumentKeys`: `_id`/`_version` required), never sent as is.
  - `route_config` checks every response against its model in localdev only, raising on a mismatch (so tests catch drift), and skips the check in every other environment for speed. The response is returned unchanged.
  - A `@pubSubDecorator` publisher's return value IS the published payload: type it, never reshape it, and pin it with `lastPublishedPayload` in a test.
  - Route params: no `datetime`/`date`/`time` (take an ISO `str` and parse it with `utils.appDayStart` / `appDayBounds` / `parseIsoInstant`), no bare `dict`/`list`/`tuple`/`Any`, a `= None` default needs `| None`. The generated handler refuses (400 "Invalid <param>") an object or a list for a scalar param (`str`/`int`/`float`/`bool`/`Literal`, or Optional of one), so a `{"$ne": null}` never reaches a query.
  - A JWT route with a `userId` param refuses (400 "Unauthorized access") any `userId` other than the JWT identity, a null one included. `roleAccess` requires `jwtRequired=True` (route_config refuses it otherwise).
  - Generated routes log which of their own params a POST sent, never values; a `createAccessToken` route logs no request data at all; a Pub/Sub push handler logs its messageId and the message's keys. A body that is not a JSON object is a 400 envelope, never a 500.
  - Errors (`routeErrors.py`): a `ValueError` is a 400 with its message (so raise one the user can act on), `PermissionError` a 403; any other exception is a real 500 with a generic message and an error id (a failed sibling call a 503), logged once without the exception's text.
  - Never put a `@computed_field` on a response model: the TS type declares it, but a raw-dict response never carries it.
- **Auth**: `loginWithGoogle` takes the client's Firebase `{idToken}`, verifies it (`AuthHandler.verifyFirebaseIdToken`; the project is `FIREBASE_PROJECT_ID` in `sharedConstants.py`, which `client/lib/firebase.ts` reads too, or the `FIREBASE_PROJECT_ID` env var), and signs in the token's uid/email; only localdev accepts a raw uid/email, and `devLogin` / `devGetUserList` answer in localdev only. Local sign-in goes through the Firebase Auth emulator (`create-star-app dev` starts it with the Storage emulator, Flask and Next.js; before cloud-setup the project id is `demo-<name>`): the emulator's tokens are unsigned, and `AuthHandler.emulatorTokensAccepted()` lets one in only when `ENVIRONMENT=localdev` AND `FIREBASE_AUTH_EMULATOR_HOST` is a loopback host, still checking audience, issuer, subject and expiry. Never relax that rule, never set `FIREBASE_AUTH_EMULATOR_HOST` on a deployed service, and never make a cloud environment accept an unsigned token. Storage access is `storage.rules` (signed-in users, `users/<uid>/` only; uploads JPEG/PNG under 10 MB). The first user of an empty Users collection becomes superAdmin through an atomic one-time claim (`Bootstrap` collection).
- **Local server**: binds 127.0.0.1; `LOCAL_BIND_HOST=0.0.0.0` in `server/.env` opens it to the LAN (with a startup warning: localdev trusts a raw sign-in identity). Outside localdev `JWT_SECRET_KEY` must be at least 32 random characters (scaffolding wrote one into `server/.env`).
- **Response compression**: app.py sends JSON and CSV bodies of 500 bytes or more as brotli or gzip (flask-compress), except the `createAccessToken` routes (BREACH). Set COMPRESS_DISABLED=1 on the Cloud Run service to turn compression off without a code deploy.
- **Tests**: `conftest.py` refuses to start unless `ENVIRONMENT=localdev` and `databaseName` ends in `Scratch` (the default `teststarCommerce` DB holds the restored prod dump, and tests wipe the DB), unsets the cloud Mongo variables and replaces pymongo's `MongoClient` with `_LocalOnlyMongoClient`, which refuses every non-local host. Its "Sign-in" section holds the Firebase fixtures (`firebase`, `anotherUser`, `emptyUsers`).
- **Parallel suites**: the suites of different repos may run at the same time on one local mongod. Each wipes only its own `*Scratch` DB, `pubSubMockDb` is only read (only the generators write it), and only `mainDb` / `TestDb` build indexes. Two runs of the same repo at once need different `*Scratch` names (e.g. `databaseName=teststarCommerce<Branch>Scratch`). Never run a `pubSubMockDataGenerator.py` while any suite runs: it rebuilds the `pubSubMockDb` collection the other suites replay. A sibling server a suite calls runs on its own `*Scratch` DB, never the one that sibling's own suite uses (e.g. ecommerce's accounting on :5000: `databaseName=testaccountingForEcomScratch`). Two ecommerce runs at once would share that one accounting server and its `testaccountingForEcomScratch` DB: a second ecommerce run needs its own accounting server on another port and DB, or must not run at the same time.
- **Stale Pub/Sub mock data**: `test_pubSubContracts.py` must always pass, and stale mock data is never "unrelated". On `Mock data is older than 3 days` or `No mock data has been consumed for the <service> service`, regenerate it, then rerun:
  1. Find the stale publishers: the `<service>` in the error, and every publisher this repo consumes (`server/PUBSUB_MAP.md`).
  2. Wait until no suite runs in any repo: no pytest or other `pubSubMockDataGenerator` process. The generator rebuilds the `pubSubMockDb` collection other suites replay.
  3. In each of those sibling checkouts, run `cd server && ENVIRONMENT=localdev databaseName=test<thatProject>Scratch python pubSubMockDataGenerator.py`. Always use a `*Scratch` DB: the generator wipes the DB it is given and does not check its name.
  4. Rerun `test_pubSubContracts.py`. If a generator fails, fix that failure or report it; the contract tests are never left red.
- **Deploys**: every push to `main` runs `cloudbuild.yaml` (build, push, run the new image as the Cloud Run job `<service>-predeploy` (`server/job_predeploy.py`: the Pub/Sub topic check and the index builds; a failure stops the deploy; a console deploy, a manual `gcloud run deploy` or a revision rollback skips it), update the Cloud Run service (its HTTP startup probe waits until app.py's `/startupCheck` answers, so the app loads on startup's full CPU; a revision that never answers fails the deploy), then refresh its `<service>-*` jobs with `server/tools/updateJobsFromService.py`) once the Cloud Build trigger is switched to it (`server/ARCHITECTURE.md`, "GCP Cloud Run Jobs"). `server/Dockerfile` refuses a build without `--build-arg BUILD_CONFIG=cloudbuild.yaml`, so a local `docker build` of `server/` needs that arg: `docker build --build-arg BUILD_CONFIG=cloudbuild.yaml server`. `updateJobsFromService.py` writes to GCP: Claude never runs it, not even with `--dry-run`. `star-app.json`'s `cloud` section holds the GCP project, the Cloud Run service and the Cloud Build trigger names (`<service>-main`; never a secret). `create-star-app cloud-setup` and `cloud-teardown` write to GCP, Atlas, Vercel and GitHub, so Claude only prints the command for the user to run (`create-star-app cloud-setup --dry-run --offline` is safe and writes nothing). `server/tools/createOrUpdateJob.py` writes to GCP too, and Claude never runs it.
- **Pub/Sub**: publishers use `@pubSubDecorator`; `pubSubAdmin.py` creates the topics and push subscriptions, and `checkPubSubTopics.py` (run by `job_predeploy.py`, the Cloud Run job `<service>-predeploy` that `cloudbuild.yaml` runs before each deploy, with the index builds) fails the deploy when a topic is missing.
- **Pub/Sub map** (`server/PUBSUB_MAP.md`; details in `server/ARCHITECTURE.md`, "The Pub/Sub map"): every publisher in the fleet, each consumer's handler and the payload paths it reads. Siblings are read at a committed git ref (this branch's name, else `main`). `test_pubSubMap.py` fails on a stale map, a broken publisher/handler edge, or a payload that misses what a handler reads, in both repos of the flow: fix it at its source (the publisher's model or the handler), never record it (`PUBSUB_CONTRACT_GAPS` is retired and fails). A contract change is done when the map is regenerated and committed in every repo of the fleet, with the same branch name checked out in each (or after merging to `main`), or the other repos read the old `main`. `python pubSubMap.py --write-all` regenerates every sibling checkout on this branch at once; commit each repo yourself.
- **Generated Pub/Sub message models** (`pubSubModels.py`; details in `server/ARCHITECTURE.md`): this repo commits `server/pubsub_models.json`, the payload model of every topic it publishes (a route's `responseModel`, else `PUBSUB_PAYLOAD_MODELS` in a publisher module that is no route). It consumes `server/objects_<publisher>.py`, generated from each publisher's manifest: never edit one, and put no logic in it. A push handler parses its message once with `message = <Fn>Message.model_validate(data)` and reads only `message`; the raw `data` only in an `except ValidationError:` fallback on that parse (`test_everyHandlerParsesItsGeneratedMessage`). Store through this repo's own models, never a dump of the message. A payload change that widens it (a new Literal member, a field made nullable or optional, a dropped field, int to float) deploys after its consumers; one that narrows or adds fields deploys before them.
- If `server/services/<name>.notFound.md` exists, read it: a sibling repo is missing on this machine and some cross-repo checks ran against a snapshot.
- **Shared files**: create-star-app is the source of truth for the files its `fleet/sharedFiles.json` lists (generic tests, `servicePortCheck.py`, the map tools, `tools/` job scripts). `test_sharedFiles.py` fails when one differs from `../create-star-app` at HEAD. Never edit one repo's copy alone: fix the template, commit it, run `python sharedFileCheck.py --write` in every repo.
- **Product photos** (details in `server/ARCHITECTURE.md`, "Product photos"): `generateProductPhotos` makes styled photos with Meta's `muse-image-1.0` (`imageModel.py`, `MODEL_API_KEY`) from the admin's own uploads under `users/<uid>/`, read through the Storage SDK by path (`photoStorage.py`; never fetched by URL). The bucket is `FIREBASE_STORAGE_BUCKET`, else `<FIREBASE_PROJECT_ID>.firebasestorage.app`; in localdev `FIREBASE_STORAGE_EMULATOR_HOST` (or `STORAGE_EMULATOR_HOST`) points it at the Storage emulator. Results go to `stores/<storeId>/photos/`, which `storage.rules` lets anyone get (never list) and only the server write; `PHOTO_DAILY_CAP_ALL` (default 1000) caps all stores' photos per day (deploying the rules, `firebase deploy --only storage`, and the bucket IAM binding are for the user to run). `setProductPhoto` puts one of the store's own photos on a product (`Product.photoUrl`). The new products form takes one photo per row; the chat then calls `makeProductPhotoChoices` per product (one a turn): it copies the original into the store's photos (no quota) and makes 3 styled ones, and the admin picks one on a `productPhotoChoice` card (original only, with `notGenerated` saying why, when no style is set, a cap is reached or the model fails). Both photo tools return the prompt the model was given (kept on `GeneratedPhoto.prompt`), which the cards show under "Prompt used". The brand colors are required by `createUserStore` (a store from before that may have none) and also go to the shop (ShopStoreResponse); the shop and the admin's chat (which re-reads the store after every saved turn) are drawn in them; the photo style goes to the admin only.
- **Delivery** (details in `server/ARCHITECTURE.md`, "Delivery"): an order is a pickup or a delivery (`fulfillment`), as the store's `deliveryOptions` offer (none said: pickup only); a delivery carries the address, pin and notes, can be booked only once the store is pinned, and costs `DELIVERY_USD_PER_KM` (0.15) US dollars per straight-line km from the store's pin, in the store's currency at the day's rate (`actions/deliveryPricing.py`; rates from open.er-api.com, cached daily in ExchangeRates, usable up to 7 days old; nothing from `freeDeliveryMinimum`, asked only when `offersFreeDelivery`), which is in the order's `total` (the km in `deliveryDistanceKm`). With one bookable way it is chosen for the customer. Order rows carry the delivery fields (`OrderDeliveryRow`); an order stored before delivery existed reads as a pickup (`OrderActions.orderRow`). The chat asks pickup or delivery in conversation, and for a delivery has the customer pin it (`showDeliveryPinForm`), then asks the address. A store may limit where it delivers to up to 10 areas the admin draws on a map (`showDeliveryZonesForm`, saved by `setMyDeliveryZones` on `Store.deliveryZones`; none: anywhere): a pin outside every one is refused on the pin form and by `createOrder` (`insideDeliveryZones`).
- **Voice** (details in `server/ARCHITECTURE.md`, "Voice"): `sendStoreVoiceMessage` / `sendAdminVoiceMessage` take `audio`, a base64 WAV (mono, 16-bit PCM, 16 or 24 kHz, 0.3 to 60 s), transcribe it with Meta's `muse-voice-transcribe-1.0` (`MODEL_API_KEY`), run it as a chat turn (`ChatActions._slottedTurn`), and return the reply plus ElevenLabs speech (`ELEVENLABS_API_KEY`, `eleven_flash_v2_5`, base64 MP3; `audio: null` when speaking fails) in the store's `voiceId` (`updateMyStoreTheme`, picked from `listVoices`), else `ELEVENLABS_DEFAULT_VOICE_ID`; `speakChatTurn` speaks a saved reply. The recording goes to Meta and the reply text to ElevenLabs; nothing logs audio, transcripts or replies. The client must send the final RIFF and data sizes (no streaming sizes); Meta gets only the samples. Daily VoiceUsage caps: seconds 1800 per customer (across stores) / 6000 per store / `VOICE_DAILY_SECONDS_ALL` (default 30000) for all stores; characters 20000 / 100000 / `VOICE_DAILY_CHARS_ALL` (default 2000000); 0 turns that direction off; an admin counts against its store's and all stores' counters. voiceModel.py is plain `requests` (no SDK), with `httpSession()` the test seam. Voice mode itself streams replies browser to ElevenLabs: the chat routes' `speak: true` adds `speech` (`VoiceActions.replySpeech`: a single-use `tts_websocket` token, the store's voice, the spoken text), issued only for a reply just saved, 6 a minute per user / 60 per store, its characters counted against the daily caps; the browser (`elevenLabsStream.ts`) plays the PCM stream, and falls back to its own voice when `speech` is null. Our key stays on the server; give the key a credit limit in ElevenLabs as the hard ceiling.
- **Chat attachments** (details in `server/ARCHITECTURE.md`, "Chat attachments"): `sendStoreChatMessage` / `sendAdminChatMessage` take `attachments`, up to 4 Storage download URLs of JPEG, PNG or PDF files (one PDF at most; none with a form answer) the caller uploaded (the client puts them under `users/<uid>/chat/`, the only folder `storage.rules` lets take a PDF; 10 MB each; the text may then be empty), checked before the slot, lock and quota, read through the Storage SDK (`photoStorage.ownFiles` / `downloadFiles`, never by URL; each file's first bytes must be its type's) and sent to Muse as base64 data URLs (image_url / file parts); a turn stores only path, type, name and size. One request sends at most 20 MB of files (this message's first, refused past it) and 50 images (a PDF weighs 50, an image 1): within what is left, the last 3 turns' files are re-read and re-sent, newest first; the others become notes. A process holds at most 60 MB of attachment bytes (`CHAT_ATTACHMENT_BYTES_IN_FLIGHT_MAX`, reserved before any download): past it a message is a 503, a history file a note. Daily ChatUsage caps per file: 20 per customer / 300 per store / `CHAT_ATTACHMENTS_DAILY_CAP_ALL` (default 3000; 0 turns them off). The quotas are given back when the request never reached Meta, or Meta was unavailable before answering; never once it answered, nor for its 400 on this message's files (on the first call only: "couldn't be read, or too many pages"). That 400 on a request whose history carried files is retried once with those as notes (same deadline and reserved bytes, no further quota; `chatHistoryAttachmentsRefused`, a count); refused again, it is the files' error when this message has any, else ours (a 503, quotas given back). The history gets only what this message leaves of the 50 images (never below 0); a message's own files are weighed only by the one-PDF rule. An admin's image note carries its tokenless URL for `generateProductPhotos`. Files go to Meta as data; no log carries a path, name, URL or content.
- **Thinking texts** (details in `server/ARCHITECTURE.md`, "Thinking texts"): every `@mcp_tool` declares `thinkingText=[...]`, required, at least 3 distinct phrases (≤ 60 characters), the chat shows while the tool runs. The client sends a random `turnKey` with each chat or voice message and polls `getChatThinking(turnKey)` each second; `_runModel` saves one of the running tool's texts at random (`chatThinking.note`, ChatThinking, cleared when the turn ends). Voice mode plays `speakChatThinking(turnKey)`: ElevenLabs speaks each (voice, text) once, kept in ThinkingSpeech and reused; `job_predeploy.py` (`syncThinkingSpeech`) deletes the clips of removed texts and speaks new ones at every deploy, never failing it.
- **Cancelling an order** (details in `server/ARCHITECTURE.md`, "Cancelling an order"): `cancelMyOrder` cancels the customer's unpaid order always, and a paid one (refunded) only as `Policy.paidOrderCancellation` says: `beforeHandover` while it is paid, `withinHours` while it is paid and within `paidOrderCancellationHours` (1 to 168) of `paidAt`; `notAllowed` or not said, never.
- **Returns** (details in `server/ARCHITECTURE.md`, "Returns"): a customer requests a return of some items of their own completed order (`requestReturn`; item positions from `getMyOrders`, a later request returns what is left, at most 10 requests per order); the admin approves or rejects it, then receives it (`receiveReturn`), which refunds it to the order's payment (`payments.refundDemoPayment`, whatever `refundMethod` says) only after the flip to received, guarded on a null `refundedAt`, and with `restock=true` puts its units back in inventory (`_version` +1). Statuses: requested, approved, rejected, received, cancelled (the customer, while requested). `objects.returnRefusal` applies the store policy: `changedMind` needs `acceptsReturns` and the `returnWindowDays` window; `defective`/`wrongItem` the `defectReportDays` window (else `returnWindowDays` when returns are accepted); each window ends with the Nth app day (UTC+8) after the handover's (`completedAt`); what the store has not said is refused with "ask the store".
- **Chat cards and forms** (details in `server/ARCHITECTURE.md`, "Chat cards and forms"): a chat reply carries `components`. Cards are built from what the turn's tools returned (`chatCards.py`), never from the model's words; forms are opened by chat-only form tools (`chatForms.py`, in `chatTools.TOOLS`, never on the MCP servers). A form or a choosing card is answered through the chat route's `form`, checked against what it answers, and the model acts on it. An admin whose store is not set up yet chats with the setup toolset only, which asks no address: once `createUserStore` succeeds the turn goes on with the admin's tools and opens the map, and the address is suggested from the pin.
- **Store reset** (details in `server/ARCHITECTURE.md`, "Store reset"): `resetMyStore(confirmName)` (an admin route, no chat or MCP tool) deletes the admin's own store (`ownerQuery`) and everything in it: Products, Orders, OrderLocks, Returns, Policies, GeneratedPhotos, Conversations and their ChatTurns (customers' included), and in Storage `stores/<storeId>/`, the admin's `users/<uid>/` except its `chat/` subfolder (`photoStorage.deletePrefix`), and of that subfolder only the files the deleted store's turns carried (`deleteOwnChatFiles`); a Storage failure is logged and the reset still succeeds. It keeps Users, Customers, Bootstrap, ExchangeRates, the usage counters (today's per-store ones are copied to the new id, so no quota comes back) and customers' uploads. `confirmName` is the store's name (case and spaces ignored), `reset` for a store not set up yet. One transaction swaps the store for a new empty one with a NEW `_id` (`createEmptyStore`, the one sign-up creates), so the old id reaches nothing; the old id's documents are deleted after it, best effort (a write racing the reset stays on the old id, an orphan: a stray OrderLock, a late Return, a chat turn or conversation, a generated photo and its row; never an order, the Products going first). The old slug is free for anyone once it commits. From `STORE_RESET_ENDS_AT` (`sharedConstants.py`, 2026-11-05T00:00:00+08:00) it is a 403 before any read (`StoreActions._now` is the clock seam) and the client hides the button; delete the route, dialog and constant in a follow-up after that.
- **Frontend**: Next.js, React, coss ui (vendored in `client/components/ui`, MIT), Tailwind CSS; Google Maps (Maps JavaScript API, `@googlemaps/js-api-loader`) for the map pin, with the browser key `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` (restricted to the app's websites; without it the pin card says the map is unavailable).
- **Store details and address** (`actions/StoreActions.py`): `updateMyStoreDetails` changes the admin's name, description, contact number, address or opening hours (never the link or currency). After a pin, `suggestStoreAddress` asks Google's Geocoding API (`geocoding.py`, server key `GOOGLE_MAPS_API_KEY`) for the pin's street address; it only suggests (null on any failure, never an error), and the chat saves it with `updateMyStoreDetails` only once the owner says yes. conftest's `_fakeGeocoding` answers for Google in every test.
- **Timezone**: UTC+8, a fixed offset (`AppConfig.Timezone`): no daylight-saving time, so a region with DST needs its own handling.
